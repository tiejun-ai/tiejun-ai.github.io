    TokenMinds: LLM-driven User Modeling for YouTube Recommendation — My Explanation and Thoughts

    August 3, 2026

    Understanding TokenMinds (Google DeepMind & YouTube) — building Gemini LLM-driven user modeling for YouTube recommendation: an encoder-decoder that emits both a dense user embedding and a set of discrete Semantic-ID user tokens, unifies long-form and short-form video in one model, and serves billions of users asynchronously from a cache. TokenMinds extends the Generative Recommendation framework PLUM from retrieval to user modeling.

    Paper: TokenMinds: Pretrained User Tokens and Embeddings for User Understanding in Large Recommender Systems (Liu et al., Google DeepMind & YouTube, June 2026)

    TL;DR#

    Generative recommendation assigns Semantic IDs (SIDs) to items and uses an autoregressive sequence model to frame recommendation as Next SID prediction. TIGER introduced SIDs, and PLUM scaled them into YouTube’s production retrieval stack by adapting a Gemini LLM.

    TokenMinds asks the obvious next question — what if users got Semantic IDs too? — and answers it with a Gemini LLM-driven user modeling system deployed on full YouTube traffic:

    • Dual output. An encoder-decoder, warm-started from PLUM’s pre-trained LLM, reads the user’s behavior history. The encoder emits a 1,152-dim dense user embedding; the decoder beam-searches 40 discrete SID-based user tokens. Both are used in downstream ranking models as user representations.
    • Cross-scenario in one model. Prepend <LFV> / <SFV> condition tokens to mark the Long-Form-Video or Short-Form-Video scenario, and decode scenario-specific tokens from a single shared encoder pass — saving 50% training compute and 31% serving compute.
    • Async serving. User representations are generated offline on a 24-hour cadence and cached; real-time user modeling requests read the cache at a 96.4% hit rate across 1.44M reads/sec, and a cache miss triggers asynchronous regeneration.

    TokenMinds confirms the practical viability of SID-based user tokens at industrial scale and demonstrates that tokens and dense embeddings provide complementary value in user modeling. On the YouTube Shorts surface, embeddings alone gave +0.05% satisfied engagement and tokens alone +0.40% — but applying both together gave +0.62%.

    Problem: User Modeling#

    User modeling is a key component of any recommender system:

    • Input: user behavior sequence — watches across long-form and short-form video, search queries, likes, dislikes, watch times.
    • Output: a representation of that user that any downstream ranking or retrieval model can consume.

    Traditionally user modeling takes the form of a dense user embedding: run the user behavior sequence through a sequence model, pool it, and output an embedding vector. It works, but has a structural ceiling — a person’s whole spectrum of interests squeezed into one vector.

    An emerging alternative is to have an LLM summarize the user into a text profile. The paper argues such LLMs capture only topical co-occurrence rather than sequential dynamics, and face the modality gap in video recommendation.

    A user token is a video SID prefix — so “this user’s next interest” is written in the same vocabulary as videos. (Diagram created for this blog, based on Sections 1 and 2 of the paper.)

    In generative recommendation frameworks such as PLUM, each video is assigned a SID — a tuple of SID tokens.

    TokenMinds’ answer: represent a user in the same discrete SID vocabulary already used for videos. A user token is literally a video SID prefix — so a user’s predicted interest and a candidate video are expressed in one shared language, and the tokens inherit the hierarchical semantic meaning that SIDs already carry.

    Furthermore, TokenMinds emits both embeddings and tokens as user modeling output, and shows that both forms have complementary value.

    Method Explained#

    TokenMinds reuses PLUM’s foundations — same SID tokenizer (an RQ-VAE over multi-modal video embeddings), same Continued Pre-Training (CPT) that teaches a Gemini LLM to treat SIDs as a new modality. If those are unfamiliar, my PLUM post explains the tokenizer and CPT, and my TIGER post covers RQ-VAE math in detail.

    TokenMinds has the following architecture:

    Input: the user signals#

    The leftmost column of Figure 1 is more heterogeneous than in a typical watch-history model:

    • Watches across both scenarios — YouTube Long-Form and Shorts, collected from multiple surfaces (homepage recommendations, watch-next suggestions), interleaved in chronological order.
    • Search queries — explicit textual intent. This is nearly free here: because CPT already put SID tokens and text in one unified vocabulary, queries can simply be interleaved into the watch sequence behind a <Search> token. The 10 most recent Search queries are used.
    • Engagement signals per watch — watch time, watch ratio, likes and dislikes, device, timestamps.

    Each watch is serialized into a small fixed token budget:

    <LFV|SFV> + 4 SID tokens + 1 soft token

    The condition token marks the scenario, the four SID tokens are the video’s SID prefix, and the soft token carries everything else — each non-SID feature is embedded separately, concatenated, and projected through an MLP down to a single vector.

    Why encoder-decoder?#

    TokenMinds deliberately uses encoder-decoder for two reasons:

    • Encoders read the full history better. Bidirectional attention captures more comprehensive sequential patterns over a long history, and a dense user embedding falls out naturally from pooling contextualized encoder states.
    • Encoder and decoder can be split at serving time. The encoder is heavy and compresses a slow-moving 1,200-watch history; the decoder is light and reflects recent behavior. Decoupling them lets you refresh a heavy encoder infrequently and a lightweight decoder frequently.

    Training: three improvements over naive next-watch prediction#

    The encoder reads history; the decoder generates SIDs for several near-future watches at once. (Figure 2 from the paper, Liu et al., 2026.)

    The Loss Function (Equation 1 from the paper, annotated for this blog.)

    The three improvements encoded in the loss function are the heart of the method:

    • Look-ahead sampling. Instead of predicting the immediate next watch W_t+1, randomly sample up to N=15 targets from the watches in the next 24 hours. The reason is that a user model should describe a broader spectrum of intent over a longer window. This also prevents overfitting to whatever the user happened to watch next.
    • SID truncation. Videos have L_full=8 codebook levels; training and input encoding keep only the prefix L=4. This is the single most important knob in the ablation. A coarse prefix names a region of the video corpus rather than one video, which encourages diversity and blunts memorization.
    • Multiple simultaneous targets, which is simply more sample-efficient in training than one target per example.

    Cross-scenario: long-form and short-form in one model#

    Long-form (LFV) and short-form (SFV) video have genuinely different consumption dynamics — Shorts are consumed in a continuous browse with no explicit click, creating a much stronger feedback loop. Usually two separate user models are used.

    The paper reports two facts that argue against that: nearly half of all users engage with both formats, and their SIDs share about 40% vocabulary overlap in the first two prefix levels (note that LFV and SFV videos share the same SID token vocabulary). User interests are not partitioned by format. And because SIDs live in a shared token space, unification is nearly free: prepend a <LFV> or <SFV> condition token to each watch and interleave both chronologically. (Search queries join the same way, with a <Search> prefix.) Condition tokens are excluded from the loss calculation — predicting them is trivial and doing so degrades quality.

    At serving time, the unified model still needs to output scenario-specific user tokens. A naive approach is Separate Per-Context Inference: running inference twice, once for LFV and once for SFV — which re-runs the encoder both times:

    Multi-context decoding: encode once, branch into per-scenario sub-batches, decode concurrently. (Figure 3 from the paper, Liu et al., 2026.)

    TokenMinds develops a smart multi-context decoding scheme, which encodes the user history once and branches decoding into parallel sub-batches, one per scenario, all sharing the same encoder hidden states — a 31% serving compute reduction (481 chips instead of 698). Training compute halves too, since one model replaces two.

    Downstream adaptation: how do you feed user tokens to a model that wants embeddings?#

    User modeling outputs user representations used by downstream ranking and retrieval models. TokenMinds outputs both user embeddings and user tokens — the embedding summarizes what the user watched, the tokens predict what they will watch next. How can downstream models use user tokens as features?

    The paper evaluates three token-to-embedding strategies:

    1. Prefix Embedding Mapping (EM) — map each user token (SID prefix) back to the mean of the original content embeddings (used as input for SID generation) of all videos sharing that prefix.
    2. N-gram Embedding — split the user token (SID prefix) into fixed-length sub-words, each with a learned embedding; sum them.
    3. SPM Embedding — same as 2, but uses SentencePiece to learn variable-length sub-words.

    (2) and (3) are collectively Learnable Embeddings (LE) — randomly initialized embedding tables trained end-to-end with the downstream model. Each of the user’s 40 tokens is embedded this way, then pooled into a single user vector.

    An online pivot study on the SFV surface settled the choice (Table 3 in the paper): LE beat the static EM mapping (+0.22% vs −0.02% satisfied engagement), so letting the downstream model learn its own embedding space for tokens wins.

    Serving: caching + async regeneration#

    Figure 4 from the paper, Liu et al., 2026.

    To make a heavy generative model viable at billion-user scale, user representations are generated in the background on a 24-hour refresh cadence and cached in a key-value store, and user model requests read the cache. On a cache miss or expiration, a background refresh service regenerates the representation.

    In production the cache serves 1.44M reads/sec at a 96.4% hit rate, and a user’s token representation costs 1,280 bytes versus 4,608 for the dense embedding.

    Experiments and Results#

    The production model is adapted from a Gemini-1.5 LLM: a 370M MoE encoder plus a 370M dense decoder, both initialized from PLUM’s CPT checkpoints, trained continuously on the latest daily data at millions of examples per day — again far more sample-efficient than Large Embedding Model (LEM) based models needing billions of interactions.

    At YouTube scale these percentages are large in absolute terms, and they are additive on top of an already heavily optimized production system.

    My Thoughts#

    Advantages and Lessons#

    • User representation as Semantic IDs. TIGER, OneRec, and PLUM showed the power of Semantic IDs as item representations. TokenMinds extends this to users and — more importantly — validates its effectiveness in large scale YouTube production.

    • Coarse item token as user token. Truncating an 8-level item SID to 4 levels is a small idea with big consequences. It gives users and items a shared vocabulary at different granularities — a user’s interest is a region of the item space, an item is a point in it. The −17% cold-start ablation shows how much value it carries.

    • Async serving enables scale up. Caching and asynchronous generation are what let one user representation be reused across many downstream models — effective reuse is key to scaling up personalized recommender systems.

    • Cross-scenario unification for free. Because everything is already tokens in a shared space, merging LFV and SFV needs just two condition tokens, and only one unified user model is needed for two surfaces.

    Disadvantages and Possible Future Work#

    • The LFV gains are thin. Satisfied engagement +0.08% and engaged users +0.02% on LFV are significant but much weaker than the SFV results.

    • A 24-hour refresh is a long time on Shorts. The cadence that makes serving cheap also means a user’s representation can be a full day stale, on a YouTube Shorts surface where interests shift within a session.

    • Learnable Embeddings add complexity. A user token (SID prefix) is already semantically well-structured and hierarchical, so it is unclear why the N-gram and SentencePiece sub-word schemes are needed on top of it.

    Big picture#

    Why it matters. Generative recommendation has focused on item representation as Semantic ID tokens. TokenMinds shows user representation is equally tokenizable, and that multiple user tokens can capture a user’s diverse interests.

    It also shows user tokens do not replace user embeddings, and they offer complementary value in user modeling.

    Industry trend. Taken together, TIGER → PLUM → TokenMinds traces a coherent path: assign items semantic tokens, teach an LLM to understand them, then use tokens for user representation. As LLM inference becomes cheaper and more powerful, we can expect more exciting LLM- and token-driven innovation in recommendation systems!
