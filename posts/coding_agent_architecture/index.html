    Anatomy of a Coding Agent: Agent = LLM + Agent Harness

    October 19, 2026

    Coding agents are among the most fascinating AI applications. They are fundamentally changing the way we build software! Where does their magic power come from? It comes from a combination of powerful LLMs and a smart agent harness: the software framework that turns LLMs into powerful agents.

    This post presents what I learned from—and my thoughts on—Sebastian Raschka’s wonderful Mini Coding Agent and his accompanying article, Components of A Coding Agent. His compact implementation, in roughly 1,000 lines of Python code, makes the architecture easy to follow. This is a fascinating study of the architecture of a typical coding agent and a clear illustration of the central idea: Agent = LLM + Agent Harness.

    The Architecture: LLM + Agent Harness#

    Figure 1. The agent harness connects model decisions to tool execution and carries the results into the next prompt.

    The architecture has three layers:

    • Model: interprets the task, reasons over the available context and tool results, and chooses the next tool call or produces a final answer.
    • Agentic loop: calls the model to generate the next action, executes tool requests, and feeds the tool execution results back into the next model call until the model returns a final answer or a limit is reached.
    • Runtime support: provides repository context, prompt assembly, tools, permissions, context reduction, and persistent state.

    A ReAct-style Agentic Loop#

    MiniAgent.ask() implements the loop. This pseudocode condenses its control flow:

    while within_step_and_retry_limits:
    raw = model.complete(agent.prompt(user_request))
    kind, payload = agent.parse(raw)

    if kind == "tool":
        result = agent.run_tool(payload["name"], payload["args"])
        record_tool_event(payload, result)
        update_working_memory(payload, result)
    elif kind == "retry":
        record_formatting_feedback(payload)
    else:
        record_final_answer(payload)
        return payload

    The harness parses each model response into one of three outcomes:

    • Tool: the model requests a tool call. The harness validates and executes it, records the result, and updates working memory. The next model call receives that tool execution result so it can decide what to do next.
    • Retry: the response is empty or malformed, such as a tool call with invalid JSON. The harness records feedback explaining the expected format and calls the model again. This recovery step makes agents more robust to LLM errors.
    • Final answer: the model provides an answer, usually inside <final>...</final>. The harness records it, returns it to the user, and ends the loop.

    Two limits control the loop’s budget:

    • max_steps caps the number of tool-call attempts.
    • max_attempts caps the number of model calls.

    The loop stops when either iteration limit is reached, or earlier when the model produces a final answer.

    Tools: How the LLM Acts Through the Harness#

    Tools allow the LLM to ask the agent harness to search, read and write code and other files, run shell commands, and spawn subagents. The model generates the request; the harness executes it and returns the tool execution result.

    LLM APIs commonly support native tool calling: the application supplies tool schemas, and the model returns structured tool calls in dedicated response fields.

    Mini Coding Agent implements its own text protocol instead, putting tool descriptions and output-format instructions directly in the prompt. Selected excerpts from build_prefix() show how it tells the model to generate a tool request:

    Rules:
- Use tools instead of guessing about the workspace.
- Return exactly one <tool>...</tool> or one <final>...</final>.
- Tool calls must look like:
  <tool>{"name":"tool_name","args":{...}}</tool>

Tools:
- read_file(path: str, start: int=1, end: int=200) [safe] Read a UTF-8 file by line range.

Valid response examples:
<tool>{"name":"read_file","args":{"path":"README.md","start":1,"end":80}}</tool>

    Here, <tool> marks the request, name selects the tool, and args supplies its inputs. parse() extracts this information from the generated text.

    Figure 2. A generated tool request becomes a checked Python call. Results, errors, and formatting feedback return to the loop.

    build_tools() registers each tool’s argument schema, description, approval flag, and Python implementation:

    ToolsPurpose
    list_files, search, read_fileFind and inspect code and other files
    write_file, patch_fileCreate or edit files
    run_shellExecute commands, including tests
    delegateSpawn a bounded child agent

    run_tool() validates the request, checks for repeated identical calls, applies approval policy, executes the tool, and clips its output. The tool execution result—or an error—enters the next model call through the transcript.

    Context Window: What Does the LLM See?#

    At each iteration of the agentic loop, the LLM needs relevant information to decide what to do next. The harness assembles this context into the input prompt, including instructions, tool descriptions, repository context, working memory, conversation history, and the current user request.

    Figure 3. The exact prompt order used by prompt(): a fixed prefix followed by session context and the current request.

    The implementation’s prompt() shows the exact layout:

    def prompt(self, user_message):
    return "\n\n".join([
        self.prefix,
        self.memory_text(),
        "Transcript:\n" + self.history_text(),
        "Current user request:\n" + user_message,
    ])
    Context componentWhat it contributes
    Stable prefixGeneral instructions, rules, tool descriptions, tool-call and final-answer examples, workspace summary
    Working memoryTask, important file paths, short notes
    Compact transcriptPrevious requests, tool calls and results, LLM responses
    Current requestThe user instruction this loop is addressing

    The stable prefix stays unchanged across all steps in a session, while working memory and the transcript evolve as the agent runs. The harness sends the assembled prompt to the LLM on each iteration. Next, let’s examine how each component is built.

    Stable Prefix: Instructions, Tools, and Workspace Context#

    build_prefix() assembles the stable prefix as follows:

    return "\n\n".join([
    "You are Mini-Coding-Agent, a small local coding agent running through Ollama.",
    "Rules:\n" + rules,
    "Tools:\n" + tool_text,
    "Valid response examples:\n" + examples,
    self.workspace.text(),
])

    General instruction establishes the agent’s identity and environment: “You are Mini-Coding-Agent, a small local coding agent running through Ollama.”

    Rules guide the LLM’s behavior and specify how the LLM formats tool calls and final answers.

    Tool descriptions tell the LLM which tools are available, what they do, and which arguments they accept.

    Examples demonstrate valid tool calls and final answers, giving the LLM concrete response patterns to follow.

    Workspace Context comes from WorkspaceContext.build(): repository root, branch, Git status, recent commits, and excerpts from AGENTS.md, README.md, pyproject.toml, and package.json when present at the root or current directory.

    The prefix is built when the agent starts and remains unchanged across subsequent agentic loop steps. This stable structure enables prompt prefix caching when supported by the LLM serving runtime.

    Working Memory: Highlighted Key Information#

    The session starts with this structure:

    "memory": {"task": "", "files": [], "notes": []}

    Each field preserves a different kind of context:

    • task stores a shortened copy of the session’s first user request, keeping the original goal visible across later steps.
    • files stores paths of recently read, created, or edited files, helping the LLM keep track of where it has been working. The list retains up to eight paths.
    • notes stores short excerpts from tool execution results and final answers, keeping recent tool results and final answers visible without including the full history. The list retains up to five notes.

    Compact Transcript: Condensed Conversation History#

    At each agentic loop step, the LLM needs relevant conversation history—including user requests, LLM responses, tool calls, and their execution results—to decide what to do next. The harness includes a condensed version in the prompt through "Transcript:\n" + self.history_text(), preserving continuity while limiting prompt size.

    Every loop iteration adds new events to conversation history. To keep it manageable, history_text() applies three reductions:

    • Clip individual events: each event is clipped to a window size, with recent events having larger windows and older events having smaller windows.
    • Deduplicate repeated file reads: omit repeated older reads.
    • Clip the overall history: limit the total size of the assembled conversation history.

    SessionStore: Persistent Conversation History and Working Memory#

    Figure 4. Stored history and working memory serve different prompt components. Persistence preserves session state; prompt construction selects its model-facing view.

    SessionStore saves the recorded conversation history and working memory together in JSON files. This allows the agent to resume a session from saved state after a failure or interruption.

    The recorded conversation history is not inserted directly into the context window. As discussed above, only its condensed view—the Compact Transcript—is included, alongside working memory and the other prompt components. This reduces the prompt size and helps the LLM focus on essential context.

    Subagents: Let the LLM Delegate Bounded Subtasks#

    Mini Coding Agent lets the LLM delegate a subtask by calling the delegate tool, implemented by tool_delegate(). For example, the LLM can delegate an investigation:

    <tool>{"name":"delegate","args":{"task":"Find which function causes the failing parser test."}}</tool>

    The harness creates a child agent that runs its own agentic loop. The design balances useful context with clear constraints:

    • Enough context to work on the subtask: the child receives the workspace context, the delegated task, and a short excerpt of the parent’s conversation history.
    • Bounded execution: the child is read-only, with file mutations blocked. Its tool steps and recursion depth are limited, preventing unbounded subagent delegation.

    Figure 5. A bounded child agent works on a delegated subtask. Its final answer becomes a tool result for the waiting parent.

    The child agent’s final answer returns to the parent agent as a delegate tool execution result.

    My Thoughts#

    A Small Codebase That Makes the Architecture Clear#

    This is a beautiful codebase that demonstrates the core architecture of a coding agent and, more generally, an agent harness. In roughly 1,000 lines of Python, it makes the structure easy to follow: we can trace how the loop, tools, context, memory, and delegation work together.

    Memory Architecture and Context Engineering#

    Agent memory architecture and context engineering remain central to effective agent engineering. Even with powerful LLMs, constructing the right context for each request requires careful design. Decisions about what to remember, omit, and compress—and how much detail to preserve—depend on budget settings and practical experience.

    As LLMs become more capable and less expensive, I expect more context engineering to be automated, especially in domains with reliable evaluation mechanisms. Letting LLMs compact conversation history, maintain useful memory, and select relevant context could reduce the need for manual context engineering.

    The Art of Subagents and Scaling With Agent Swarms#

    I particularly like how this coding agent exposes delegation as a tool, allowing the LLM to decide when to create a subagent. It gives the model autonomy to organize work around subtasks. Although this implementation keeps delegation tightly bounded, a more general harness could extend the same idea to recursively create and coordinate agent swarms.

    I see potential for scaling benefits: increasing the number of subagents and total computation could help agents solve more challenging and complex problems. Whether this produces a reliable scaling law would need to be studied.

    This is a beautiful and powerful idea, but it needs proper control. Limits on recursion depth, agent count, computation, and permissions are essential to balance capability and safety of AI Agents.
